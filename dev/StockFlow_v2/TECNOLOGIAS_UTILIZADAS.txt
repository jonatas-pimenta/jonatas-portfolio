3. BANCO DE DADOS: SQLITE 3
================================================================================

O QUÊ É:
SQLite é um sistema de gerenciamento de banco de dados relacional embarcado.
Armazena dados em um único arquivo (.db) sem necessidade de servidor separado.
É o SGBD mais utilizado do mundo.

PARA QUE ESTÁ USANDO:

```
self.conexao = sqlite3.connect("estoque.db")
self.conexao.execute("PRAGMA foreign_keys = ON")
```

Isso cria o arquivo se não existir e ativa integridade referencial (FK).

TABELAS CRIADAS:
1. usuarios: username, senha_hash (bcrypt), perfil (ADM/gerente/operador), ativo
2. produtos: nome, categoria, preço, quantidade, estoque_mínimo, fornecedor, data
3. movimentacoes: produto_id, tipo (entrada/saída), quantidade, data, usuário
4. fornecedores: nome, telefone, email, endereço, data_cadastro
5. clientes: nome, telefone, email, endereço, data_cadastro

SCHEMA EXEMPLO (usuarios):
┌─────────┬──────────────┬──────────────────────┬────────────┬────────┐
│ id (PK) │ username (U) │ senha_hash           │ perfil     │ ativo  │
├─────────┼──────────────┼──────────────────────┼────────────┼────────┤
│ 1       │ ADM          │ $2b$12$K1q2wX...    │ ADM        │ 1      │

POR QUE ESCOLHEMOS SQLITE:
1. Sem servidor - não precisa de MySQL, PostgreSQL rodando

4. SEGURANÇA - HASHING DE SENHAS: BCRYPT
================================================================================

O QUÊ É:
Bcrypt é um algoritmo de hash de senhas adaptativo baseado em Blowfish.
Implementa "adaptive hashing" - fica mais lento com hardware mais rápido.

PARA QUE ESTÁ USANDO:
- Hash seguro das senhas dos usuários lors do cadastro
- Verificação de senha no login sem nunca armazenar a senha original
- Proteção contra força bruta e rainbow tables

COMO FUNCIONA AQUI:

CADASTRO DE USUÁRIO:
Senha original: "minhasenha123"
                    ↓
         bcrypt.hashpw()
                    ↓
Hash gerado: "$2b$12$K1q2wXyZ.vAbCdEf1234567890abcdefghijklmnop"
                    ↓
Armazenado no banco: senha_hash = "$2b$12$K1q2wXyZ.vAbCdEf..."

LOGIN:
Usuário digita: "minhasenha123"
                    ↓
         bcrypt.checkpw(senha_digitada, hash_armazenado)
                    ↓
Retorna: True (igual) ou False (diferente)

CÓDIGO NO PROJETO:
```python
# Cadastro
import bcrypt
senha_hash = bcrypt.hashpw(senha.encode('utf-8'), bcrypt.gensalt())
self.conexao.execute("INSERT INTO usuarios (senha_hash) VALUES (?)", (senha_hash,))

# Login
senha_hash_armazenada = self.conexao.execute(
    "SELECT senha_hash FROM usuarios WHERE username = ?", (username,)
).fetchone()
if bcrypt.checkpw(senha.encode('utf-8'), senha_hash_armazenada):
    print("Login bem-sucedido")
```

POR QUE ESCOLHEMOS BCRYPT:
1. Não é reversível - impossível recuperar a senha original do hash
2. Força bruta é cara computacionalmente - tem "fator de trabalho"
3. Proteção contra rainbow tables através de salt aleatório
4. Recomendado por OWASP (Open Web Application Security Project)
5. Padrão de ouro na indústria há 20+ anos
6. Implementação de biblioteca "bcrypt" é simples e confiável

POR QUE DUAS FUNÇÕES E NÃO USAR SÓ UM HASH SIMPLES (MD5/SHA1):
- MD5/SHA1 são RÁPIDOS demais - permitem bilhões de tentativas por segundo
- Um atacante pode testar senha "123456" contra 10 bilhões de hashes por segundo
- Bcrypt há fator de trabalho 2^12 (4096) iterações mínimas
- Aumenta em factor de ~1000x o tempo de cada tentativa
- 10 bilhões de tentativas MD5 = 10 segundos
- 10 bilhões de tentativas Bcrypt = ~116 dias
- Por isso MD5/SHA1 nunca devem ser usados para senhas

POR QUE NÃO USAMOS ALTERNATIVAS:
- scrypt: Similar a Bcrypt mas menos popular, maior consumo de memória
- Argon2: Mais moderno mas menos documentado, overkill para projeto pequeno
- PBKDF2: Antigo, menos seguro que Bcrypt atualmente

5. CRIPTOGRAFIA - ENVELOPE HÍBRIDO: RSA + AES-256-GCM
================================================================================

Este é o ponto mais crítico. Por que DUAS criptografias e não apenas uma?

================================================================================
5.1 - AES-256-GCM (Criptografia Simétrica)
================================================================================

O QUÊ É:
AES (Advanced Encryption Standard) é um algoritmo de criptografia simétrica.
"256" significa chave de 256 bits. "GCM" (Galois/Counter Mode) adiciona
autenticação do payload.

PARA QUE ESTÁ USANDO:
- Criptografar o conteúdo do banco de dados para backup
- Proteger a confidencialidade dos dados

COMO FUNCIONA:

BACKUP (Criptografia):
Arquivo estoque.db (50MB)
         ↓
  [Gerar chave AES aleatória de 256 bits]
  [Gerar nonce aleatório de 96 bits]
         ↓
  AES-256-GCM.encrypt(plaintext, nonce, chave)
         ↓
  Resultado: ciphertext (enviado para JSON)
         ↓
  Arquivo armazenado: estoque_backup_20260603_120000.enc.json

RESTORE (Descriptografia):
estoque_backup_20260603_120000.enc.json
         ↓
  [Ler ciphertext e nonce do JSON]
  [Descriptografar com chave -> precisa ter a chave!]
         ↓
  AES-256-GCM.decrypt(ciphertext, nonce, chave)
         ↓
  Resultado: plaintext (banco original)

VERIFICAÇÃO DE INTEGRIDADE:
GCM não só criptografa, mas também autentica. Se alguém modificar 1 bit
do ciphertext, o GCM detecta e rejeita.

```python
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

aes_key = os.urandom(32)  # 256 bits
nonce = os.urandom(12)    # 96 bits
aesgcm = AESGCM(aes_key)

# Encriptar
ciphertext = aesgcm.encrypt(nonce, plaintext, associated_data=None)

# Decriptar
plaintext = aesgcm.decrypt(nonce, ciphertext, associated_data=None)
```

POR QUE AES-256 E NÃO 128 OU 192:
- AES-128: 2^128 combinações possíveis (recomendado para 2030+)
- AES-192: 2^192 combinações possíveis
- AES-256: 2^256 combinações possíveis (recomendado para além de 2030)
- A diferença de performance entre 128, 192 e 256 é negligenciável em hardware moderno
- Por segurança futura, 256 é o padrão recomendado
- NIST recomenda AES-256 para dados altamente classificados

POR QUE GCM E NÃO CBC/ECB:
- ECB: "Eletronic Code Book" - NÃO SEGURO, padrões visíveis no ciphertext
- CBC: "Cipher Block Chaining" - seguro mas não autentica
- GCM: "Galois/Counter Mode" - seguro, rápido e autentica tudo
- GCM detecta modificações não autorizadas do ciphertext

================================================================================
5.2 - RSA-OAEP-SHA256 (Criptografia Assimétrica)
================================================================================

O QUÊ É:
RSA é um algoritmo de criptografia assimétrica usando chaves públicas/privadas.
"OAEP" (Optimal Asymmetric Encryption Padding) é um modo seguro de uso.
"SHA256" é o hash usado no padding.

PARA QUE ESTÁ USANDO:
- Proteger a chave AES simetrica
- Permitir que a chave AES seja armazenada de forma segura sem a chave privada

COMO FUNCIONA:

SETUP (Gera par de chaves):
```
openssl genrsa -out private_key.pem 2048
openssl rsa -in private_key.pem -pubout -out public_key.pem
```

Resultado:
private_key.pem (SECRETO, nunca compartilhar!!!)
public_key.pem (pode ser compartilhado públicamente)

BACKUP (Proteger a chave AES):
1. Gerar chave AES-256 aleatória (256 bits)
   → aes_key = os.urandom(32)

2. Encriptar conteúdo com AES
   → ciphertext = AESGCM(aes_key).encrypt(...)

3. Proteger a chave AES com RSA público
   → wrapped_key = public_key.encrypt(aes_key, OAEP...)

4. Armazenar em JSON:
   {
     "wrapped_aes_key_b64": "MIIBIjANB...(wrapped_key em base64)",
     "ciphertext_b64": "aGVsbG8gd29ybGQ=...",
     "nonce_b64": "abc123xyz..."
   }

RESTORE (Desproteger a chave AES):
1. Ler JSON com wrapped_key
   → wrapped_key_b64 = envelope["wrapped_aes_key_b64"]

2. Descriptografar com RSA privado (passphrase protegida)
   → private_key = carrega private_key.pem
   → aes_key = private_key.decrypt(wrapped_key, OAEP...)

3. Usar aes_key para descriptografar o ciphertext
   → plaintext = AESGCM(aes_key).decrypt(...)

```python
from cryptography.hazmat.primitives.asymmetric import padding
from cryptography.hazmat.primitives import hashes

# Encriptar (apenas com chave pública)
wrapped_key = public_key.encrypt(
    aes_key,
    padding.OAEP(
        mgf=padding.MGF1(algorithm=hashes.SHA256()),
        algorithm=hashes.SHA256(),
        label=None,
    ),
)

# Decriptar (apenas com chave privada)
aes_key = private_key.decrypt(
    wrapped_key,
    padding.OAEP(
        mgf=padding.MGF1(algorithm=hashes.SHA256()),
        algorithm=hashes.SHA256(),
        label=None,
    ),
)
```

================================================================================
5.3 - POR QUE USAMOS AMBAS (RSA + AES) E NÃO APENAS UMA?
================================================================================

Esta é a questão crítica que o usuário perguntou.

OPÇÃO 1: Usar apenas AES-256-GCM

Vantagens:
- Mais simples
- Um pouco mais rápido

Desvantagens:
❌ A chave AES também precisa ser armazenada em algum lugar
❌ Se armazenarmos a chave AES junto com os dados criptografados, um atacante
   tem acesso a ambos - sem segurança!
❌ A chave AES teria que estar hardcoded no código fonte - péssimo!
❌ Não há "master key" para desencriptar backups se necessário

OPÇÃO 2: Usar apenas RSA

Vantagens:
- Poderia armazenar dados diretamente com RSA

Desvantagens:
❌ RSA é muito mais lento para dados grandes
   - Para um backup de 50MB: levaria minutos para encriptar
   - AES é milhares de vezes mais rápido
❌ Tamanho de chave RSA para 256 bits de segurança = 2048 bits
   - Encriptando 50MB com RSA geraria arquivo gigantesco
❌ RSA não foi projetado para grandes volumes de dados

OPÇÃO 3: RSA + AES (O QUE FAZEMOS) ✓

Vantagens:
✓ AES criptografa os 50MB rapidamente
✓ Chave AES é gerada aleatória a cada backup
✓ Chave AES é protegida com RSA (chave pública gerada localmente)
✓ Se a chave privada RSA estiver offline, dados estão protegidos
✓ Mesmo que alguém roube o arquivo .enc.json, não consegue descriptografar
  sem a chave privada RSA
✓ Performance: segundos de encriptação vs minutos com RSA puro

FLUXO COMPLETO - POR QUE AMBAS:

Cenário de Segurança:
Um atacante invade o servidor/nuvem e consegue:
- Arquivo de backup: estoque_backup_20260603_120000.enc.json ✓

Com apenas AES (sem RSA):
"Achei um arquivo .enc.json"
"Mas preciso da chave AES..."
"Achei! Está escrita no banco de dados também" ❌ SEM PROTEÇÃO
→ Atacante descriptografa tudo facilmente

Com apenas RSA:
"Preciso criptografar 50MB com RSA"
"Demoraria 10 minutos..." ❌ MUITO LENTO
"E o arquivo ocuparia 500GB!" ❌ IMPRATICÁVEL

Com RSA + AES (O QUE FAZEMOS):
"Achei um arquivo .enc.json"
"Contém uma chave AES criptografada com RSA"
"Mas não tenho a chave privada RSA..." ❌ NÃO CONSEGUE ABRIR
"A chave privada está segura com passphrase no meu laptop"
→ Arquivo é inútil sem a chave privada!

PADRÃO INDUSTRIAL - TLS/HTTPS:
Este mesmo padrão é usado em TLS (https://), o protocolo que protege
toda a internet:
1. Criptografia simétrica (AES) protege os dados em volume
2. Criptografia assimétrica (RSA) protege a chave simétrica inicial

A internet usa exatamente a mesma combinação porque:
- É rápida (AES)
- É segura (RSA protege a chave)
- É comprovada (usado por bilhões de pessoas)

6. CRIPTOGRAFIA - VERIFICAÇÃO DE INTEGRIDADE: SHA-256
================================================================================

O QUÊ É:
SHA-256 (Secure Hash Algorithm 256-bit) é um algoritmo criptográfico de hash.
Recebe qualquer entrada e produz um hash único de 256 bits (64 caracteres hex).
É determinístico: mesma entrada = mesmo hash sempre.
É unidirecional: impossível reconstruir entrada a partir do hash.

PARA QUE ESTÁ USANDO:
- Verificar que o backup não foi corrompido durante transmissão
- Validar autenticidade do arquivo persistido

COMO FUNCIONA:

BACKUP:
Arquivo compactado: estoque.tar.gz
         ↓
  sha256(arquivo) → "f1d2d2f924e986ac86fdf7b36c94bcad46221b4cf539b37a0f4a3ff60c6b8c6d"
         ↓
  Armazenado no JSON:
  {
    "ciphertext_sha256": "f1d2d2f924e986ac86fdf7b36c94bcad46221b4cf539b37a0f4a3ff60c6b8c6d"
  }

RESTORE:
1. Ler arquivo backup
2. Calcular sha256(arquivo) → "f1d2d2f924e986ac86fdf7b36c94bcad..."
3. Comparar com hash armazenado
4. Se diferentes: ARQUIVO FOI CORRUPTO! Abortar restore.
5. Se iguais: OK, prosseguir com descriptografia

```python
import hashlib

# Calcular
arquivo_hash = hashlib.sha256(conteudo_arquivo).hexdigest()

# Comparar
if arquivo_hash == hash_esperado:
    print("✓ Arquivo íntegro")
else:
    print("✗ Arquivo corrompido!")
```

POR QUE SHA-256 E NÃO SHA-1/MD5:
- MD5: Quebrado cryptanaliticamente, colisões encontradas
- SHA-1: Quebrado, NIST recomenda descontinuar
- SHA-256: Seguro até 2030+, recomendado por NIST
- SHA-512: Ainda mais seguro mas desnecessário para este uso

7. COMPRESSÃO: TAR + GZIP
================================================================================

O QUÊ É:
- TAR (Tape Archive): formato que junta múltiplos arquivos em um
- GZIP (GNU Zip): algoritmo de compressão que reduz tamanho

PARA QUE ESTÁ USANDO:
- Compactar arquivo estoque.db antes de criptografar
- Reduzir tamanho de transmissão para Google Drive
- Histórico de backups sem ocupar 200GB de espaço

COMO FUNCIONA:

BACKUP (Compressão):
estoque.db (50MB)
    ↓
  tar c estoque.db → estoque.tar (50MB, sem compressão)
    ↓
  gzip estoque.tar → estoque.tar.gz (5MB, comprimido)
    ↓
  [Encriptar estoque.tar.gz com AES-256-GCM]
    ↓
  estoque_backup_20260603_120000.enc.json (5.1MB, criptografado)

RESTORE (Descompressão):
estoque_backup_20260603_120000.enc.json
    ↓
  [Descriptografar com AES-256-GCM]
    ↓
  estoque.tar.gz (5MB, descriptografado)
    ↓
  tar xzf estoque.tar.gz
    ↓
  estoque.db (50MB, restaurado)

```python
import tarfile

# Comprimir
with tarfile.open("estoque.tar.gz", "w:gz") as tar:
    tar.add("estoque.db", arcname="estoque.db")

# Descomprimir
with tarfile.open("estoque.tar.gz", "r:gz") as tar:
    tar.extractall()
```

POR QUE USAR TAR + GZIP:
- Reduz tamanho de 50MB para ~5MB (90% de redução!)
- Economiza espaço em disco
- Economiza banda de internet para Google Drive
- Padrão Unix consolidado há 40 anos
- Nenhuma perda de dados (compressão sem perda)

POR QUE NÃO ZIP:
- ZIP também seria funcional
- TAR é mais portável em Unix/Linux
- GZIP é mais uniforme que ZIP (TAR | GZIP pipeline)
- Ambos funcionariam, TAR/GZIP é preferido em Linux

8. INTEGRAÇÃO COM NUVEM: GOOGLE DRIVE + OAUTH 2.0
================================================================================

O QUÊ É:
Google Drive é serviço de armazenamento em nuvem do Google.
OAuth 2.0 é protocolo de autenticação que permite acesso a contas Google sem
armazenar senhas.

PARA QUE ESTÁ USANDO:
- Enviar backups criptografados para Google Drive
- Acesso remoto aos backups sem risco local
- Redundância: dados locais + backup em nuvem
- Acesso de múltiplos dispositivos aos backups

COMO FUNCIONA:

FLUXO OAUTH 2.0 DE USUÁRIO (oauth_user):

1. Primeira vez que usuario executa backup:
   - Sistema abre navegador
   - Redireciona para login Google
   - Usuario entra com gmail.com
   - Google pergunta: "Permitir acesso ao StockFlow?"
   - Usuario clica "Sim"
   - Google gera token_google_drive.json
   - Token é armazenado localmente

2. Próximos backups:
   - Sistema lê token_google_drive.json
   - Usa token para acessar Google Drive
   - Envia arquivo sem pedir nova autenticação

CÓDIGO:
```python
from google.oauth2.credentials import Credentials
from google_auth_oauthlib.flow import InstalledAppFlow
from googleapiclient.discovery import build

SCOPES = ['https://www.googleapis.com/auth/drive.file']

# Primeira vez
flow = InstalledAppFlow.from_client_secrets_file(
    'credentials.json', SCOPES)
creds = flow.run_local_server(port=0)

# Salvar token para reutilizar
with open('token_google_drive.json', 'w') as token:
    token.write(creds.to_json())

# Próximas vezes
creds = Credentials.from_authorized_user_file('token_google_drive.json')

# Usar credenciais para acessar Drive
drive_service = build('drive', 'v3', credentials=creds)

# Upload
file_metadata = {'name': 'backup.enc.json'}
file = drive_service.files().create(
    body=file_metadata,
    media_body=MediaFileUpload('backup.enc.json'),
    fields='id'
).execute()
```

SEGURANÇA:
- Senha Google NUNCA é armazenada localmente
- Token pode expirar (refresh token automático)
- Token pode ser revogado a qualquer momento
- Arquivo enviado para Drive permanece criptografado (Google não consegue ler)

POR QUE GOOGLE DRIVE:
1. Integrado ao Android/Chromebook/PC Windows
2. Interface web amigável
3. Gratuito até 15GB
4. Sincronização automática em dispositivos
5. Histórico de versões (recuperar versão anterior do arquivo)

POR QUE OAUTH 2.0:
1. Seguro - senha nunca compartilhada com aplicação
2. Padrão industrial - usado por 99% das apps
3. Token pode ser revogado sem alterar senha
4. Granulação de permissões - app só acessa o que precisa

9. MANIPULAÇÃO DE DADOS TABULARES: PANDAS
================================================================================

O QUÊ É:
Pandas é biblioteca Python para manipulação de dados em tabelas (DataFrames).
Oferece operações similares a SQL mas em Python.

PARA QUE ESTÁ USANDO:

from pathlib import Path

backup_dir = Path("outputs/backups")

if arquivo.exists():

arquivo.parent.mkdir(parents=True, exist_ok=True)

conteudo = arquivo.read_text()

print(arquivo.name)  # "backup_20260603.enc.json"

print(arquivo.suffix)  # ".json"

print(arquivo.parent)  # "outputs/backups"

20. MULTI-THREADING: THREADING
================================================================================

O QUÊ É:
threading permite executar múltiplas tarefas "simultaneamente" em Python.
Útil para operações longas que não bloqueiam UI.

PARA QUE ESTÁ USANDO:
- Executar backup em background (não congela GUI)
- Sincronizar backups pendentes sem pausar operação

COMO FUNCIONA:

```python
import threading

def backup_longo():
    # Demora 5 minutos
    fazer_backup_completo()
    print("Backup concluído")

# Na interface GUI:
# Sem threading (RUIM - congela UI):
# backup_longo()  # UI fica travada por 5 min

# Com threading (BOM - UI responsiva):
thread = threading.Thread(target=backup_longo)
thread.daemon = True  # Encerra ao fechar app
thread.start()
# UI continua responsiva enquanto backup roda

# Aguardar conclusão
thread.join()  # Aguarda thread terminar
```

ONDE USAMOS:
- GUI aguarda backup terminar sem congelar
- Usuário pode continuar usando aplicação
- Modal de progresso mientras backup sincroniza

POR QUE THREADING:
- GUI responsiva
- Melhor experiência de usuário
- Operações longas não travam a aplicação

POR QUE NÃO ASYNC/AWAIT:
- Threading é simples para este caso
- Async é mais complexo e overhead
- Threading suficiente para I/O simples
